# ADR-0019: WireGuard tunnel and peer changes (staged)

- Status: accepted
- Date: 2026-11-15
- Deciders: project owner

## Context

ADR-0009 gives a read-only WireGuard status view and lists tunnel and peer edits as out of scope, each
needing its own decision. Operators still cannot add a peer or change a tunnel without the OPNsense UI.
The lab uses WireGuard as its VPN, so a bad change can cut the operator's own access.

What the OPNsense API does (from `opnsense/core` master: `Wireguard/Api/ServerController.php`,
`ClientController.php` and `ServiceController.php`; **to be confirmed on the 26.7.8_2 lab before any
write is marked verified**). WireGuard now lives in core, not the plugin repository.

- **Tunnels** are "servers": `searchServer`, `getServer/{uuid}`, `addServer`, `setServer/{uuid}`,
  `delServer/{uuid}`, `toggleServer/{uuid}`, and `keyPair`. The body root key is probably `server`.
- **Peers** are "clients": `searchClient`, `getClient/{uuid}`, `addClient`, `setClient/{uuid}`,
  `delClient/{uuid}`, `toggleClient/{uuid}`, plus helpers `pks`, `listServers`, `getServerInfo`. The
  body root key is probably `client`.
- **Linking:** a peer carries a `servers` field (comma-separated tunnel uuids). A tunnel carries a
  `peers` field (comma-separated peer uuids). `setClient` and `delClient` also edit the tunnels' `peers`
  lists, so one peer change can touch several tunnels.
- **Keys:** a tunnel has a private and a public key. A peer has a public key and an optional preshared
  key. `keyPair` and `psk` ask the firewall to generate keys, so a private key travels in a response.
- **Apply:** writes save to the config only. They take effect after
  `POST /api/wireguard/service/reconfigure`. Whether this restarts every tunnel and drops active peers
  is **unconfirmed**; the safe assumption is that it can.
- No dry run, savepoint or revert, as for the other staged kinds.
- **Privilege:** the lab API user has only read access to WireGuard status ("VPN: WireGuard: Status").
  The privilege for config endpoints is not yet confirmed on the lab; the status privilege does not
  cover `server` and `client`.

## Decision (proposed)

### 1. Same staging model as ADR-0005, ADR-0017 and ADR-0018

New change kinds `wireguard_peer` (and `wireguard_tunnel`, if the owner accepts tunnels in scope). The
`kind` column is a free string, so **no migration**. Same table, status machine, four-eyes rules,
`allow_writes` gate, per-firewall apply lock, SHA-256 stale fingerprint, result snapshot and audit
records. No automatic rollback; undo is a new reviewed request from the stored base snapshot.

Roles as before: `network_admin` stages and reviews, only `admin` applies, `security_admin` and
`read_only` are view-only, a `network_admin` cannot approve their own request.

The apply procedure reuses the shared resolver one (lock, stale check, write, separate audited
`reconfigure`, read back), generalised from `ResolverSpec` where that is cheap. If `reconfigure` fails
the request is `failed`, with the message that the change is saved but **not active**. Existing
Dnsmasq and Unbound behaviour must not change.

### 2. Scope of the first release (owner decision 2026-11-15: tunnels writable too)

- **Peers:** create, update, delete and enable/disable.
- **Tunnels:** create, update, delete and enable/disable, as a second change kind
  `wireguard_tunnel`. **Every tunnel change, including a toggle, is high risk** (a tunnel edit can cut
  the admin's own VPN access). Fields: `name`, `listen port`, `tunneladdress`, optional `mtu`,
  `disableroutes`, `enabled`, and the linked peers. **Open issue:** a tunnel needs a private key, which
  this app must never handle (see section 3 and the questions). Tunnels are built after peers, with
  their own lab test.
- **Out of scope in any case:** config download, QR codes, the config builder, instance
  start/stop/restart (each needs its own ADR), and any private-key handling.

### 3. Keys (security-sensitive)

- **A private key is never accepted from the browser, stored, logged or returned.** The backend
  drops private and preshared keys from every response, as ADR-0009 does.
- A new peer's key pair is generated by the person's own WireGuard client. They paste only the
  **public key** into the form. This app never calls `keyPair` or `psk`.
- **Preshared keys:** not settable in the first release. A peer that already has one is shown as
  "preshared key set", and the key is neither read nor changed.
- **Public keys:** shown to `admin` and `network_admin` (they are not secret and identify the
  peer). This needs the owner's agreement, because ADR-0009 hid them.
- Public key validation: 44-character base64 that decodes to 32 bytes. A duplicate public key is
  refused at stage time and again at apply.

### 4. Field subset (anything else is refused)

**Peer:** `name` (required), `pubkey`, `tunneladdress` (one or more host addresses such as
`10.10.0.5/32` or `/128`, no wider network), `servers` (existing tunnel uuids; at least one),
optional `serveraddress` and `serverport` for a peer's endpoint, optional `keepalive`, `enabled`.
Local validation: name rules, address parsing, sizes capped, tunnel uuids must exist and be real
tunnels. Not settable: preshared key, DNS, MTU, any private key.

**`tunneladdress` must be inside the target tunnel's own network and must not overlap another
peer's address.** An address overlap is refused at stage time and re-checked at apply.

### 5. Risk

**High risk** (admin approver, name typed at apply):
- any **delete**;
- **disabling** a peer (it cuts someone's access, possibly the operator's own);
- **changing a peer's public key, tunnel address or tunnels** (this can move access to another key).

**Normal risk:** creating a new peer, enabling a peer, or changing only its name or keepalive.

Creating a peer grants network access, but a reviewer must still approve it, and a `network_admin`
cannot approve their own request. If the owner prefers, creation can also be high risk (see
questions).

### 6. Apply procedure

Lock the firewall, re-check status and the stale fingerprint, confirm the peer still exists and
matches its fingerprint (the `set` calls are upserts), call the one write operation, call
`reconfigure` as a separate audited operation, read the peer back and store the result. The
confirmation dialog states that **WireGuard may restart and active tunnels may drop**.

New registry operations, all `verified=False` until the lab test:
`wireguard.peers.list`, `.add`, `.update`, `.delete`, `.toggle`, `wireguard.tunnels.list` and
`wireguard.reconfigure`. Lists are read-only and need no `allow_writes`. The toggle uses the explicit
state form (`toggleClient/{uuid}/1` and `/0`) as in earlier toggles, if the lab confirms it.

### 7. Visibility

Peer and tunnel lists (names, public keys, addresses, endpoints) are shown to `admin` and
`network_admin`, matching ADR-0017 and ADR-0018. `security_admin` and `read_only` see them only inside
change requests they may view, as today. The existing status view (ADR-0009) is unchanged.

### 8. Frontend

On the existing VPN page, add "Peers" and "Tunnels" tabs for `admin` and `network_admin`. Peers has a
table of what is on the firewall, its open requests, create/edit/delete/toggle actions and a diff
against the current object. Tunnels is read-only. Proposals go to Administration, Changes for review
and apply. The status view stays as the first tab.

### 9. Tests, dependencies and the lab

Mocked OPNsense (`respx`) for every operation: stale and duplicate detection (public key and
address), address-in-tunnel checks, risk rules, role and four-eyes rules, `allow_writes`, apply order
including a `reconfigure` failure, keys never present in any response, and audit rows. Frontend tests
for the form and role views. **No new dependency.**

The lab test (extending `scripts/e2e-lab-hosts.sh`) creates a throwaway peer with a freshly generated
**public key only** (generated in the test, no private key kept) and an address in a documentation
range or an unused tunnel address, then edits, disables, enables and deletes it. It confirms the
privilege, the body root keys, whether `reconfigure` drops active peers (checked first on the
throwaway tunnel state), and that the user's own VPN stays up.

### 10. Build order

1. Registry, normaliser, schema, staging, apply spec and list endpoint for peers, with tests.
2. Frontend tab, with tests.
3. Lab test, then mark the operations verified and update the docs.
4. Tunnel writes (`wireguard_tunnel`), with tests, the frontend tab and a lab test using a throwaway
   tunnel on an unused port, then mark verified.

## Consequences

- Operators can add, change and remove VPN peers with review, without handling private keys here.
- Every apply may restart WireGuard. The UI says so before apply.
- The config privilege is likely broader than the feature (it covers tunnels and keys), as accepted
  for earlier writes. `allow_writes` limits the blast radius per firewall.
- Users generate their own key pair and must paste the public key. No config file or QR is produced.
- A self-approving admin can still grant a hostile key access. High-risk rules and four-eyes stop a
  single `network_admin`, but not that.

## Alternatives considered

- **Generate key pairs on the firewall and hand the config to the user.** Rejected: a private key
  would pass through the backend and the browser.
- **Tunnels and peers together in the first release.** Rejected: tunnel edits are the most likely
  way to lock out the admin and also hold the private key.
- **Treat every peer change as high risk.** Possible, but it makes routine onboarding as heavy as a
  delete. Offered as an option below.
- **Config download or QR code.** Rejected for now: needs the private key or an unreviewed secret
  flow.

## Owner decisions (2026-11-15)

All accepted: (1) tunnels are writable too, not only peers; (2) creating a peer is normal risk, while
delete, disable and key, address or tunnel changes stay high risk and every tunnel change is high risk;
(3) option A: the firewall generates a new tunnel's private key, this app sends none and drops it from
every response; (4) admin and network_admin may see public keys in lists; (5) preshared keys stay
unsettable and unreadable; (6) the lab API user gets the WireGuard config privilege; (7) the lab test
may create, edit, disable and delete a throwaway peer and tunnel; (8) lists are visible to `admin` and
`network_admin` only (taken as the recommended default).

Not started. Peers first, then tunnels.
